# 提案：主题 / 场景 / 文件夹 —— 三层各管一件事（讨论稿）

> **状态：讨论稿（2026-09-23，第四轮）。** 这一轮**只写文档、不动代码**。
> 第四轮：认下"主题只是用户自己的分组"（叫"科研"或叫"打卡"都行，App 不预设语义），
> 并因此**纠正一处设计错误**：字段等声明挂**文件夹**，不挂主题（见 §5）。
> 第三轮按用户拍板的新词重写：**主题 = 内容**、**场景 = 记录方式**，两者管不同层面的事；
> 此前 AGENTS §4 与 VISION §6 对"主题 / 场景"的用法**作废**（见 §2 的退废清单）。
> 与 AGENTS.md / ARCHITECTURE_IMPL 冲突时以它们为准（它们描述的是**当前**实现，尚未按本稿改口）。

## 1. 一句话

**主题 = 这条记录讲的是什么内容**（科研 / 旅游 / 挑战 / 读书 / 工作……）；
**场景 = 这条内容是"怎么记下来"的**（随心记一句 / 认真写一篇 / 拍照打卡……）。
前者管内容，后者管**界面与录入的特化**；两者不是一回事，也不该互相绑死。

**而主题只是"用户自己的分组"，App 不给它任何功能含义**：爱打卡的人完全可以建一个主题叫
「打卡」（那本来是个场景的名字），把跑步打卡、背单词打卡都放进去；爱写字的人可以建一个
主题叫「写作台」，在里面写小说、写周报、写读书笔记。**想怎么用是用户的事** ——
这正是解耦换来的东西：主题是数据、场景是代码，两者互不牵制。

磁盘上就是**外面套一层目录**：外层目录 = 主题，内层文件夹 = "绑一个场景的一堆记录"，
再里面 = 一条条记录（现在的结构原样不动）。

## 2. 术语（第三轮拍板，旧的作废）

| 概念 | **新用词** | 谁管 | 代码标识 |
|---|---|---|---|

| 用户可点的容器（一个文件夹 = 一堆记录 + 一个场景） | **文件夹** | —— | `Folder` / `FolderMeta`（不动） |
| 软件风格（配色 / 字体 / 圆角 / 预设） | **外观** | 全窗口 | `--fv-*` / `preset.*`（不动） |
| 一条记录 | **记录** | —— | `Entry`（不动） |

| 旧说法 | 出处 | 现在的说法 |
|---|---|---|

## 3. 磁盘：三层，零新增字段

```text
<用户选的目录>/
├── vault.json
├── .framevault/trash/<原目录名>/
├── 科研/                            ← 主题：用户自己分的组（叫什么都行）
│   ├── 论文笔记/                     ← 文件夹：绑"认真写作"，字段是「实验编号」
│   │   ├── folder.json              { scene: "认真写作", fields: [实验编号…] }
│   │   └── 2026-09-23 周报：第一次消融实验/{entry.json, note.md}
│   └── 实验打卡/                     ← 文件夹：绑"拍照打卡"，字段是「实验轮次」
│       ├── folder.json
│       └── 2026-09-24 第三次实验记录/{entry.json, note.md, 2026-09-24_实验_03.jpg}
├── 打卡/                            ← 主题也可以就叫"打卡"：App 不预设主题是什么
│   ├── 跑步打卡/                     ← 同样是"拍照打卡"这个场景，字段换成「距离 / 配速」
│   │   ├── folder.json
│   │   └── 2026-09-22 早跑 3km/{entry.json, note.md, 2026-09-22_跑步打卡_01.jpg}
│   └── 背单词/                       ← 还是"拍照打卡"，字段是「单词数」
│       ├── folder.json
│       └── 2026-09-23 第 12 天/{entry.json, note.md}
└── 未归类/                          没有主题（或没有文件夹）的记录
    └── 2026-09-23 随手记一句/
```

**认目录的规则只有一条**（延续存储 v2 的"按结构识别，不按名字"）：
一级目录带 `folder.json` = **文件夹**；不带 = **容器**，容器里既可以放文件夹、也可以直接放记录（后者即"未归类"）。

因此：

- **主题 = 一个容器目录的名字**（位置派生，跟"归属由物理位置派生"同一条规矩）→ **不用给 `FolderMeta` 加字段**；
- 根下直接摆文件夹 = **没有主题**，老仓库照样读得出来；主题也可以先不建（新用户不必先分类）；
- 主题改名 = 改目录名（磁盘为准，跟现在的手动改名规则一致）。

## 4. 现在那 4 个内置模块，各归各位

现在的 4 个"功能主题"其实是**内容与记法混在一起**的四个混合体。按新词拆开：

| 现在的 id | 按新词是什么 | 落地后 |
|---|---|---|
| `builtin.plain`（普通日记） | **场景**：随心记一句（+ 照片） | 保留为场景「随心记」 |
| `builtin.writing`（写作台） | **场景**：认真写一篇（一屏一篇） | 保留为场景「认真写作」 |
| `builtin.challenge`（挑战） | **场景**：拍照打卡（含连续天数/进度）+ **主题**：挑战（目标天数这类是内容侧参数） | 场景「拍照打卡」保留；「挑战」变成**主题** |
| `builtin.travel`（旅行） | **主题**：旅游（地点、见闻都是内容）；记法其实是"随心记 + 照片" | **作为代码模块消失**，变成主题，复用「随心记」这个场景 |

这也正面印证了上一轮的发现：**四个模块其实只有两三种场景**（版式），其余都是内容侧的差异。
`builtin_scenes()` 那份注册表将来的内容是**场景清单**（随心记 / 认真写作 / 拍照打卡），
主题不进这个注册表（主题是数据，随目录走）。

## 5. 第四轮纠正：声明挂**文件夹**，不挂主题

第三稿把"内容字段（实验编号、地点）"划给了主题。用「打卡」这个例子一试就发现不对：
同一个主题下的**跑步打卡**要「距离 / 配速」、**背单词**要「单词数」——
字段是"**这一堆记录**"的属性，不是主题的。所以：

| 谁 | 管什么 | 形态 |
|---|---|---|
| **场景**（代码，少数几个） | 这一类记录**怎么录入、怎么呈现**；并给出**默认声明** | 组件 + manifest（今天的 `scenes/<id>/`） |
| **文件夹**（数据） | 这一堆记录绑哪个场景；**这批记录有哪些字段**、媒体怎么命名、有哪些配置 | `folder.json`：`scene` + 新增的声明块（`fields` / `nameTemplate` / 配置） |
| **主题**（数据） | **分组与标签**（用户自己的分类）；可选地给新建的文件夹一份**默认声明**做便利 | 目录名（可选 `topic.json` 放图标 / 默认声明 / 外观推荐） |

```jsonc
// <主题目录>/<文件夹>/folder.json
{
  "id": "…", "name": "跑步打卡", "order": 3, "pinned": false,
  "scene": "拍照打卡",                       // 场景（记法）：UI 与录入据它特化
  "fields": [ { "key": "distance", "label": "距离", "type": "number", "unit": "km" } ],
  "nameTemplate": "{date}_{field:distance}_{n}"
}
```

**好处**（正是你这个例子换来的）：同一个场景可以被无数种内容复用 ——
"拍照打卡"这一个场景，跑步用它、背单词用它、实验打卡还用它，各自声明各自的字段；
反过来同一个主题里想换记法，建个新文件夹就行。

**这一处是本项目里唯一一次"代码搬成数据"**：今天 `entryFields` 挂在场景模块的 manifest 上
（所有绑同一场景的文件夹共享一套字段），将来变成
**场景模块提供默认、文件夹声明实际生效**（用户在界面上能改，见 §7 第 7 条）。
