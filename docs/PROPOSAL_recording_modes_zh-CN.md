# 提案：题材与记录方式分开（讨论稿）

> **状态：讨论稿（2026-09-23 起）。** 这一轮**只写文档、不动代码**。
> 结论没拍死的地方都在 §6「待讨论」，每条都给了选项与我的建议 —— 你挑完再开工。
> 与 AGENTS.md / ARCHITECTURE_IMPL 冲突时以它们为准（它们描述的是**当前**实现）。

## 1. 一句话

**题材（科研、旅游、挑战……）与记录方式（随手记一句、认真写一篇、拍照打卡）是两根正交的轴。**
题材是"这些记录归在哪儿、属于哪件事"；记录方式是"**这一条**是怎么记下来的"。
所以同一个题材里三种记法都该能写，记录方式**不跟题材绑定**。

现状恰恰是绑死的：写作台这个题材里只能写长文，挑战这个题材里只能打卡，
普通日记/旅行里只能写一两句 —— 换记法就得换个题材（换个文件夹）。

## 2. 现状与代码证据

| | 现在的做法 | 你想要的 |
|---|---|---|
| 题材 | 就是一个**代码模块**（`scenes/<id>/`：组件 + 声明 + 样式），要改三处（组件目录、`registry.ts`、Rust 的 `builtin_scenes()`） | 一个题材 = 一份**声明**（数据），不写代码 |
| 记录方式 | 由题材决定（写作台=长文、挑战=打卡、日记/旅行=短记） | 由**每一条记录**决定，同一个题材里三种都能用 |
| 两者关系 | 一根轴：换记法 = 换题材 | 两根轴：题材管归类与声明，记录方式管这一条怎么记 |

代码里的证据（4 个内置主题，实际只有 2 种"版式"）：

| 主题 | 文件与行数 | 真相 |
|---|---|---|
| 普通日记 | `PlainScene.tsx` 21 行 | 与旅行**逐字相同**的两个组件（`SceneComposer` + `EntryTimeline`） |
| 旅行 | `TravelScene.tsx` 21 行 | 同上，差别只在字段与占位文案 —— **纯数据差异，却各占一个模块** |
| 挑战 | `ChallengeScene.tsx` 275 行 | 时间线 + 照片墙视图 + 连续天数统计（`challengeStats.ts` 87 行）+ "一张照片一条记录"的录入编排 |
| 写作台 | `WritingScene.tsx` 238 行 | 长文版式（左列表 + 一屏编辑器） |

`manifest` 已经是纯数据（字段 / 配置 / 命名模板 / 外观推荐 / `note` 标记），
Rust 那边只有一个 4 项的封闭注册表加一个 `is_known_scene` 校验（`commands/folder.rs:72`、`:114`）——
也就是说，"题材 = 数据"这条路**已经铺了一半**，缺的是把"记录方式"从题材里拆出来。

## 3. 目标形状

三层各管一件事：

| 层 | 管什么 | 形态 |
|---|---|---|
| **核心** | 记录怎么存、怎么改、有哪些能力 | 代码（`vault/` + `useSceneData` + 公共件）。**正文永远是 `note.md`，与记法无关** |
| **记录方式** | **这一条**怎么录入、在列表里怎么呈现 | 少数几种，代码实现 + 注册表。建议起步三种：**简记 / 长文 / 打卡（照片为主）** |
| **题材** | 归类容器 + 这一类的公共声明 | 数据：名称、图标与短语、可选字段、媒体命名模板、默认记录方式、可选统计、外观推荐 |

一个例子（同一个"科研"文件夹里，三种记法并存，列表按时间混排）：

```text
科研/                              ← 题材：只要声明"实验编号"这个字段、命名模板用 {date}_{field:expNo}_{n}
├── 2026-09-22 随手记了一句/
│   ├── entry.json                 kind: "note"（简记）
│   └── note.md                    "今天跑通了 baseline，明天加消融。"
├── 2026-09-23 周报：第一次消融实验/
│   ├── entry.json                 kind: "essay"（长文）
│   └── note.md                    # 一屏写完的长文
└── 2026-09-24 第三次实验记录/
    ├── entry.json                 kind: "checkin"（打卡：照片为主，文字可选）
    ├── note.md
    └── 2026-09-24_实验_03.jpg
```

界面上的含义（两句话）：**录入时给一个"怎么记"的入口**（三个并列的小入口，或者一个输入框 + "写长文"按钮），
**列表里每条记录按它自己的记法呈现**（简记直接显示文字、长文显示标题与摘要、打卡显示照片）。

## 4. 落地要点（真要开工时按这个顺序）

1. **磁盘**：`Entry` 加一个记法标记（`kind`，`#[serde(default)]`，老记录默认"简记"）。
   正文仍是 `note.md`、照片仍在记录目录里 —— **记法不改变任何文件的位置**，
   所以它只是"展示与录入的偏好"，不是新的数据形状（判据见 AGENTS §6）。
2. **核心**：`note` 从"由题材声明的字段"变成**每条记录天生就有**（现在靠 manifest 的 `note: true` 路由，
   那一步可以退场：题材只声明它额外要的字段，比如"实验编号"）。
3. **记录方式**：三种起步，每个是核心里的一个小单元（录入 + 呈现），注册表一行；
   题材**推荐**一种默认记法，用户每次都能改。
4. **题材**：变成数据。放哪儿见 §6 第 1 条 —— 这决定了 `folder.json` 要不要存内联声明。
5. **旧数据**：挑战的"连续天数"要提炼成核心能力（`stats: ["streak"]`），它现在是题材私有代码；
   普通日记与旅行本来就该是同一个东西（合并），写作台降级成"长文记法"而不是一个题材。

## 5. 明确不做（这一轮不碰）

- 不动磁盘布局（存储 v2 刚落地）。
- 不做"题材 DSL / 插件市场"（VISION §3.2 / §3.9 那一层）——这一轮只把**形状**理顺，
  让将来的题材=数据能自然接上。
- 不做自动判断记法（"看你写得多就自动当长文"）——先让用户自己选，理由见 §6 第 2 条。

## 6. 待讨论（每条给了选项和我的建议）

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | 题材的定义放哪儿 | ① 程序内置一份题材目录（加题材 = 加声明 + 发版）② 允许用户在应用里自定义（声明内联进 `folder.json`）③ 两者都要 | **③ 先做①**：内置目录先跑通，自定义后加。理由：`folder.json` 里塞声明要动 schema，值得等形状稳定了再动 |
| 2 | "怎么记"谁来定 | ① 每次录入时用户自己挑 ② 按内容自动判断 ③ 由题材给默认值 | **① + ③**：题材给默认，用户随时能改；"自动判断"最容易猜错，而且改起来像数据被偷改了 |
| 3 | 一个题材里要不要有"字段"（科研的实验编号、旅游的地点） | ① 要（题材声明额外字段，存 `fields[题材id]`，与今天一致）② 不要，字段一律用标签代替 | **①**：字段是分题材最实在的差别（也是命名模板 `{field:<key>}` 的来源） |
| 4 | 列表里混排三种记法，还是允许"只看某一种" | ① 混排（时间线里长的短的都在）② 加个筛选/分组 ③ 像挑战那样给"照片墙"这类切换视图 | **① 起步，②③以后再说**：先把"同一个题材里三种都能写"跑通，展示形态的优化放到后面 |
| 5 | 挑战的统计（连续天数）算谁的 | ① 核心提供 `stats: ["streak"]`，题材声明即可 ② 还是留在题材里 | **①**：纯计算、不改磁盘形状 → 按 AGENTS §6 判据该进核心；否则每个题材都要自己写一遍 |
| 6 | 命名（"记录方式"叫什么） | ① 记法 ② 记录方式 ③ 形态 | **记法**（短、不撞车）：题材 / 记法 / 外观 三者各占一个词，避免和 VISION §6 已拍板的"主题=外观"打架 |

## 7. 与其它文档的关系

- **VISION**：§3.4 的"随心记 → 深入记录**升级**链路"在本模型里天然成立（同一条记录改记法即可，
  数据不搬）；§3.2 的"20 个场景"从"写 20 个组件"降到"写 20 份声明"；§3.9 的插件将来贡献
  **记法（版式）与能力**，题材永远只是数据 —— 扩展面更小更稳。
- **AGENTS §6**：判据不变 —— 会改磁盘形状的进核心（正文 `note.md`、照片住记录目录），
  只影响呈现的（记法怎么排、题材怎么声明）留在题材/记法这一层。
- **存储 v2（刚落地）**：本提案**不动**磁盘布局；`kind` 是一个 `#[serde(default)]` 的小字段。
- **PRD**：§4.9 功能主题那节将来要按本模型重写（等 §6 拍完再动）。
