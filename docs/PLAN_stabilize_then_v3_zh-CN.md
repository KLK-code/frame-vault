## 0. 两条判据 + 四条护栏

**判据**（所有取舍都拿它裁）：

1. **内容形态不预设**：一条记录 = 正文 + 媒体 + 字段，谁多谁少都合法。
2. **层级只表达「归属」，归类一律进数据**：
   - 归属（记录在哪个文件夹、照片属于哪条记录）留在目录里 —— 换来删除/撤销/改名/搬家原子且便宜、拖照片进目录即被收养。
   - 归类（组、标签、排序）进数据 —— 换来换组只写几十字节、同步不产生"删+建"。

**四条护栏**（写进 AGENTS，越界即 bug）：

1. **只在仓库里写**：写入范围 = 仓库 + 应用数据目录（缩略图/索引）。仓库外一个字节都不写。
2. **仓库外只读，且必须由用户主动选择**：不主动遍历、不"发现设备上所有照片"。将来的"相册迁移"必须是单独一个明确动作。
3. **导入永远是复制，原文件不动**；永远不做"导入后删原文件"。
4. **删除只针对仓库内，且是移到回收站**；仓库外永不删除。

## 1. 问题汇总（症状 → 根因 → 影响）

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| P1 | 安卓上"字存不进去"，报 `记录目录不完整（缺 entry.json）` | 迁移期过渡桥 `impl AsVault for Path/PathBuf` 把 `content://` 路径包装成**桌面文件系统**句柄 | 编辑 / 改标题 / 删除 / 撤销 / 加照片**全部失效**；桌面全绿，只在 SAF 上成立 |
| P2 | 安卓上卡 | ①27 个命令里 26 个是**同步命令**（跑在主线程），SAF 上几十次跨进程查询压住 UI；②重复扫描（媒体列表扫两遍并逐条再找目录、不需要撤销视图也读回收站、全仓扫描后按文件夹过滤、**打字自动保存后重扫全仓**） | 已修一半：jank 16.5% → 10.9%，90 分位 31ms → 19ms；99 分位仍有 ~100ms 尖刺 |
| P3 | **"读不到"被当成"不存在/为空"** | 正文读取失败退化成空串；SAF 探测失败退化成 `false`；`save_entry` 对**任何**读取错误进入新建分支；对账在"扫描不完整"时也写回 | 一次临时权限问题/存储抖动 = "正文空了""照片被删了""记录需要新建"→ **可能覆盖或丢数据**（实测：`save_entry` 会用同一 id 新建，出现两条同 id 记录） |
| P4 | **删除空文件夹会连带删掉别的文件** | `delete_folder` / `delete_topic` 只检查"有没有记录目录/文件夹"，然后递归删除整个目录 | 目录里放个 PDF 或未识别的子目录，会被一起删掉 |
| P5 | **自动保存会丢尾部输入** | 编辑器 220ms 防抖后才把文本交给父组件，**卸载时直接取消计时器**；写作台与时间线各自实现保存，无统一排队/重试/版本确认 | 打完字立刻切场景/切页，最后几个字没落盘；"已保存"不代表真的落盘 |
| P6 | **安卓上原图/视频读不出来** | `SafStore::read_bytes` 仍是桩（返回"还没接"） | 缩略图能看，点开大图/视频 404；此前"安卓照片能看了"的说法**不成立** |
| P7 | SAF 写入的"原子"承诺不成立 | 顺序是"写 tmp → 删旧 → tmp 改名"，末步失败时旧文件已经消失；正文与元数据分两次写，无整体恢复 | 崩溃/中断窗口内可能丢内容，且无法恢复 |
| P8 | 未知字段会被旧版本擦掉 | serde 读时忽略未知字段，写时不写回 | 插件/新版本写的字段，用旧版本打开一次就丢 |
| P9 | `moveDocument` 判断错误 | Kotlin 注释写"SAF 没有 move"，实际 Android 有 `DocumentsContract.moveDocument`（取决于 provider 是否声明支持） | 安卓上换组/回收站走了"递归复制+删除"这条重路（也让我此前"分组必须进数据"的论据站不住） |
| P10 | 每次列目录产生大量跨进程查询 | 接口设计：按"名字逐段回查"解析路径，而 SAF 列表本可一次给出文档 id / 类型 / 大小 / 修改时间 / 能力标志 | 安卓上每次刷新都贵；缓存只是压次数的补丁 |
| P11 | 保存/长任务不绑仓库会话 | 长任务执行中途才读"当前仓库" | 切仓库可能混入旧结果；`vaultfs://` 地址里没有仓库身份，切仓库后旧 `<img>` 会解析到新仓库 |
| P12 | 场景声明与视图耦合；`useSceneData` 依赖含视图的注册表 | 数据能力与场景实现形成回环 | 数据层被迫知道视图；未知字段/缺失场景的行为没有明确规则 |

## 2. 方案（每条问题对应的处置）

| # | 处置 |
|---|---|
| P1 | **删掉过渡桥**，领域函数明确接收 `&Vault`，记录位置作为独立参数 —— **让遗漏存储后端直接编译失败** |
| P3 | **错误语义三态（四态）化**：不存在 / 无权限 / 暂时不可用 / 内容损坏分开。规则：**只有明确"不存在"才能新建**；**只有完整成功的扫描才能确认文件消失**；**读取失败不得触发清空或修复性写入**；列表失败时保留旧状态并标记"可能过期" |
| P4 | 删除前**列出全部实际子项**，只允许删除我们自己的元数据；有其它文件就拒绝并说明；**列目录失败一律拒绝删除**（文件夹与主题同等对待） |
| P5 | **统一保存协调器**：草稿状态放在不随界面切换销毁的位置；失焦/切页/卸载前**先向编辑器取最新文本**（不依赖防抖）；同一记录串行保存；"已保存"只在对应版本落盘成功后显示；失败可重试 |
| P6 | 打通 `SafStore::read_bytes`（先 base64，阶段 3 换流式），让 `vaultfs://` 能取原图/视频 |
| P7 | **可恢复写入顺序**：旧文件 → `.bak` → tmp 改名成正式 → 成功后删 `.bak`；多文件操作（正文 + 元数据）明确阶段与恢复路径 |
| P8 | 读写保留未知字段（`extra` 兜底），保证"读一遍写一遍"不丢别人写的字段 |
| P9 | 真机实测 provider 是否支持 `FLAG_SUPPORTS_MOVE`；支持就走 `moveDocument`，否则保留可恢复的复制流程 |
| P10 | 让 SAF 接口**一次列目录带回文档 id 与能力标志**，后续操作直接用 id，不再按名字回查 |
| P11 | 长任务/查询响应/媒体地址**绑定发起时的仓库身份**；前端丢弃过期响应 |
| P12 | 场景声明（纯数据）与场景视图分离；明确未知字段保留、缺失场景的通用查看方式 |
| — | **安卓主力后端**：改用"所有文件访问权限 + 直接路径"（自建目录浏览器），SAF 退为兜底；并用类型区分"仓库内路径"与"外部来源"，让"拿外部路径去写"编译不过 |

## 3. 执行计划

### 阶段 1 · 功能修复（先做，做完你手机上就是"能用"的状态）

| 任务 | 验收标准 |
|---|---|
| 1.1 拆桥：删 `impl AsVault for Path/PathBuf`，领域函数收 `&Vault` + 独立位置参数 | 编译通过；删桥后**编译器会点出所有漏网调用点**；`cargo test` 全绿 |
| 1.2 错误语义四态化；`save_entry` 只在"确实不存在"时新建；对账只在完整扫描成功时进行；列表失败不清 `media[]` | 故障注入用例通过；**损坏 JSON** 的场景给出明确提示而不是新建；不再出现"两条同 id 记录" |
| 1.3 删除保护（文件夹 + 主题） | 目录里放 PDF → 删除被拒绝且文件仍在；目录读不出来 → 拒绝删除 |
| 1.4 统一保存协调器 | 打一串字**立刻**切场景/切页/切照片页，回来字还在（桌面 + 真机各验一遍）；保存失败可重试，"已保存"不再撒谎 |
| 1.5 打通 `SafStore::read_bytes` | 手机上点开大图能看到原图；视频能播（进度跳转留到阶段 3） |
| 1.6 `moveDocument` 实测与采用 | 真机日志显示走了原生移动（不复制数据）；不支持时自动退回可恢复复制 |
| 1.7 `list_entries` 按文件夹收窄 | 进场景耗时有可对比的日志数据 |

**阶段 1 的端到端验收（真机）**：新建 → 打字 → 立刻切走再回来 → 编辑 → 改名 → 删除 → 撤销 → 加照片 → 看大图。
每一步都要**同时看三处**：界面、终端日志、磁盘上的真实文件与目录。

### 阶段 2 · 安卓主力后端切换

- `MANAGE_EXTERNAL_STORAGE` 权限声明 + 引导页（说明为什么需要）；
- 自建目录浏览器（列目录选仓库），比系统 SAF 树选择器好用，也绕开"官方插件不支持选目录"；
- 拿到权限 → `VaultRef::Fs(真实路径)`，走 `NativeFs`；拿不到 → 回落 SAF；
- 四条护栏 + `VaultPath` 类型（仓库内路径）与"外部来源"类型分开；
- 可选：导入后的媒体调一次 `MediaScannerConnection`，让照片在系统相册也可见。

**验收**：真机上新建的仓库是真实路径；桌面与手机读写同一仓库；权限被撤销时给出人话错误而不是静默失败。

### 阶段 3 · 写入可靠性与媒体流式

- 可恢复写入序列（`.bak`）+ 多文件操作阶段化；
- 视频流式读取 + Range（拖动进度可用，不再整段进内存）。

**验收**：写入中途被中断后原内容仍可恢复；大视频可拖动进度、内存占用平稳。

### 阶段 4 · 业务操作层 + 查询/索引 + 全库图库

- 把**已存在**的四条流程（保存 / 追加媒体 / 移动 / 恢复）收拢成一层业务操作（不造通用事务框架）；
- 列表改用 `EntrySummary`（不拿"没读正文的 Entry"冒充完整记录，**用类型阻止它被写回**）；
- 后端按文件夹/媒体条件直接查询 + 分页 + 摘要；
- 本地索引库**按需引入**（倾向 SQLite；前提：删掉索引后用户数据完整可恢复）；
- 后台生成缩略图（限并发、文件被替换后失效重建）；
- 全库图库视图：仓库级照片、一条日记一张卡片、顶部文件夹筛选、点进去全屏、另有纯照片网格。

**验收**：大仓库首屏与切换达到明确耗时目标；删除索引后能完整重建；图库在真机上滚动流畅。

### 阶段 5 · v3 存储定稿（唯一一次重写磁盘形状）

- 分组进数据：`groups.json`（组 id / 名字 / 顺序）+ `folder.json.groupId`；组名改动只改一处；
- 取消 `未归类`（没有文件夹的记录直接摆根下）；
- 去掉 `folderId`，但**先补上撤销所需的"原父目录、原字母名"**（且不能只存在可丢弃的缓存里）；
- 元数据放哪：评估 front matter，**与目录布局分开决策**；必须回答"**纯照片的记录**（没有正文）元数据挂在哪"；
- 字段瘦身：去 `sceneVersion`、每条记录里的 `schemaVersion`、暂不用的 `tags`；`title`/`day` **不从目录名推导**（目录名可被任意改名，不能同时承担不可丢失的业务字段）；
- 记录**继续占一个目录**（不采用"同名配对"的平铺：用户只改一半时无法判定归属，且引用只能表达"看到过"、不能表达"归谁"）。

**验收**：外部改名、移动、重复 id、损坏文件四种情况都有明确且被测试钉住的行为；`docs/`、`AGENTS.md`、README 同步。

### 阶段 6 · 自由管理

标签 UI + 批量多选/拖拽 + 聚合筛选视图 + 相机（第一屏即拍/记）。

## 4. 贯穿全程的三件事

1. **故障注入测试**：读失败 / 写到一半 / 移动中断 / 并发保存 / 外部改名 五类，在内存存储、真实文件系统两种后端上都跑（需先给内存后端补"造故障"的能力）。当前的 98 个测试只证明"桌面一切正常"，这正是 P1 能溜过去的原因。
2. **一份权威的 Vault 格式规范**：文件身份、归属规则、错误语义、冲突处理集中一处；讨论稿 / 已批准方案 / 已实现状态明确区分，历史方案标注被谁替代。
3. **每阶段的真机验收**：桌面全绿不等于能用（P1、P6 都是这么漏掉的）。

## 5. 明确不做（继续推迟）

- **目录嵌套**：用"组 + 标签 + 筛选"顶住；真需要时给组加一个 `parent` 字段即可，磁盘不用动。
- **AI 语义识别 / 人脸**、**全文检索**：维持既有推迟决定（全文检索是索引到位之后的事）。
- **Google Play 上架**：`所有文件访问` 权限需要专项申报，记录类应用未必获批。现阶段以自己安装 APK 为主；真要上架时，SAF 那条兜底路线就是给那时准备的。
