## 1. 这是个什么软件

**一句话**：一个**开放、本地优先**的跨平台个人记录仓库 —— 用户的数据就是磁盘上的普通文件（JSON / Markdown / JPG / MP4），
App 只是它的宿主与界面。不是日记软件，也不只是相册：**自由记录生活中的各种事情**（一句话、长文、照片、视频，
可以只有文字，也可以只有照片）。

**技术**：Tauri 2（Rust 后端 + 系统 WebView 前端，React 19）。桌面 Windows/macOS 已可用；
**安卓已能出包并在真机跑起来**（通过 SAF 让用户自己选一个目录当仓库）。

**已经能用的**：仓库/文件夹/记录的增删改、拖动排序、置顶、Markdown 所见即所得编辑器（CodeMirror 6，源码/实时渲染/只读三模式）、
照片导入与缩略图、按场景特化的录入界面（随心记 / 写作台 / 拍照打卡 / 旅行）、回收站与撤销、外观预设、
安卓端 SAF 目录选择与文本读写。

## 2. 目标（2026-09-25 明确）

用户要的形态：

1. **内容形态不预设** —— 一条记录可以是"一句话 + 三张照片"，也可以是一篇长文，也可以只有一张照片。
2. **用户侧干净** —— 打开文件夹看到的是**人能直接读懂的东西**（Markdown 和照片），而不是一堆程序用的小文件。
3. **照片要好找** —— 不需要先知道"它在哪条日记里"，应该能直接看整个仓库的照片。
4. **文件夹层要好管理** —— 分类、重组不该是"搬文件"。
5. **数据可迁移** —— 换机器、备份、同步、别的工具直接读，都不能出问题。

两条用来裁决所有取舍的判据：

- **A. 内容形态不预设**：记录 = 正文 + 媒体 + 字段，谁多谁少都合法。
- **B. 层级只表达「归属」，归类一律进数据**：
  - 归属（记录在哪个文件夹里、照片属于哪条记录）留在目录结构里 —— 换来"删除/撤销/改名/搬家 = 一次目录操作、原子且便宜"、
    "用户把一张照片拖进记录目录就被自动收养"。
  - 归类（属于哪个组、有哪些标签、排第几）进数据 —— 换来"换组 = 写几十字节"、"同步不产生删+建"。

## 3. 面临的问题

### P1 · 安卓上"字存不进去"（最急，是我们代码的 bug，不是格式问题）

- **症状**：手机上新建记录成功、列表里也有，但一编辑就报
  `记录目录不完整（缺 entry.json）：content://…/2026-09-25 好卡`，正文文件是 0 字节。
- **根因**：迁移期留下的一座过渡桥（`impl AsVault for Path/PathBuf`）会把"一条路径"包装成**桌面文件系统**的句柄。
  安卓上这条路径是 `content://` 树 URI，桌面文件系统根本找不到它。
- **影响面**：编辑、改标题、删除、撤销、加照片**全部失效**（这些动作第一步都要"按目录读一条记录"）；
  新建与列列表恰好不经过它，所以看起来"基本能用"。
- **为什么测试没抓到**：桌面上路径就是真路径，98 个自动化测试全绿。**这个 bug 只在 SAF 上成立。**
- **磁盘上的数据是完好的**（`entry.json` 内容合法、`folderId` 与 `folder.json` 对得上），只是读不到。

### P2 · 卡（已修一半，另一半待修）

两个原因：

1. **命令跑在主线程**：项目里 27 个后端命令有 26 个是同步的，而列表、导入这些都要读盘。
   桌面上文件系统快，看不出来；SAF 上每次操作是跨进程查询，几十次全压在 UI 线程上。
2. **重复扫描**：媒体列表扫两遍并逐条再找一次目录、不需要撤销视图时也读回收站、
   `list_entries` 全仓扫描后按文件夹过滤、**打字自动保存后重扫整个仓库**。

**已修**（2026-09-25）：26 个命令改为异步、媒体列表改单趟、保存后不重扫、安卓侧加了"一次扫描内有效"的路径缓存。
**实测**：jank 帧比例 16.53% → 10.89%，90 分位帧时间 31 ms → 19 ms，99 分位仍有 ~100 ms 尖刺。

### P3 · 分组占了一层目录

现行布局：**主题（一层目录，无 `folder.json`）→ 文件夹（`folder.json`）→ 记录（目录）**。

- "把文件夹换到另一个主题" = **真实搬目录**。桌面是一次 rename（便宜）；安卓 SAF 没有原生 move，
  实现是"递归复制 + 删旧" —— 一个装着几十张照片的文件夹换组，要复制几百兆。
- 同步上也不友好：目录搬动 = 删一个 + 建一个，记录的身份/缩略图/历史都可能跟着漂。

### P4 · 照片找不到

照片住在记录目录里，所以"找一张照片"必须先知道它在哪条日记里。日记一多，照片就被"记录"这一层遮住了。
**这是浏览方式的问题，不是存储位置的问题。**

### P5 · 定位叙事与文档不一致

`AGENTS.md` 开篇仍写着"照片与视频日记 Vault"，而愿景文档（`VISION_zh-CN.md` §1）自己标着一条待裁决：
"第一叙事到底是『影像日记』还是『随心记』"。用户现在明确：两者都不是，是**自由记录**。

### P6 · 一些小账

`未归类` 是个特例容器；`folderId` 是"归属"的第二份说法（位置已经说了同一件事）；
`entry.json` 里 `tags` 是空占位、`sceneVersion` 恒为 0 且无人读取；空正文也会建一个 0 字节的 `note.md`；
`vaultfs` 自定义协议目前一次读完整文件（大视频吃内存、无法拖动进度）。

## 4. 本次讨论已经定下的

| # | 决定 | 理由 |
|---|---|---|
| D1 | **分组进数据**：`groups.json`（组名/顺序/空组）+ 每个文件夹的 `folder.json` 记 `group` | 换组从"复制几百兆"变成"写几十字节"；同步友好 |
| D2 | **组的配置放独立的 `groups.json`，不塞进 `vault.json`** | `vault.json` 是身份文件（"有它才算仓库"），不该长业务数据。改造后仓库根下只有 `vault.json` + `groups.json` 两个配置文件 |
| D3 | **取消 `未归类` 这个特殊容器** | 没有文件夹的记录直接摆根下；扫描规则本来就是"带 `folder.json` = 文件夹 / 带 `entry.json` = 记录" |
| D4 | **去掉 `folderId`**（随 v3 一起） | 归属=物理位置，字段是第二真相，会打架 |
| D5 | **标签先不做**，但列入最后阶段的待办；这轮把它从"写出来的字段"里去掉 | 用户明确：先解决关键问题 |
| D6 | **组暂不支持"组里套组"**，但数据里预留位置 | 用户表示暂时不需要；真需要时加一个 `parent` 字段即可，磁盘不用动 |
| D7 | **照片页 = 整个仓库的照片**，按时间线展示"一条日记一张卡片"，顶部用**文件夹筛选**（不搞层级嵌套）；另给"不分日记的纯照片网格"开关 | 用户明确要"不要嵌套很多"；层级永远是平的 |
| D8 | **记录继续占一个目录**（现行），照片住在记录目录里 | 归属留在文件系统换来"删除/撤销/改名/搬家"原子且便宜，以及"拖照片进目录即被收养" |

## 5. 候选方案（待外部评审）

### 方案块 A：元数据放在哪里

`entry.json` 现在装的东西分三类：**推不出来的**（用户输入的自定义字段、手动排序顺序、身份 id、创建/修改时间）、
**能推导但有代价的**（标题/日期 ← 目录名、`folderId` ← 位置、照片名册 ← 扫目录、删除状态 ← 在不在回收站）、
**纯噪音**（每条记录一份的 `schemaVersion`、`sceneVersion`、暂不用的 `tags`）。

| 候选 | 形态 | 收益 | 代价 |
|---|---|---|---|
| **A1（现状）** 每条记录一份 `entry.json` | `好卡/` 里 `entry.json` + `note.md` + 照片 | 读写简单；元数据独立，不与正文互相干扰 | 用户侧不干净（多一个程序用的小文件在眼前晃） |
| **A2** 元数据写进正文头部（front matter，Obsidian 式） | 一条记录 = 一个 `.md`（头部一小段 YAML） | **用户侧最干净**；一条记录就是一个文件；别的工具能直接读 | 编辑器必须保住那段头部（用户容易顺手删掉，要做成折叠/防删）；**文件夹没有正文可挂载，`folder.json` 仍需保留** |
| **A3** 元数据进数据库 | 磁盘只剩 `.md` + 照片 | 用户侧也干净 | **致命**：数据库在应用私有目录、不随仓库走，换机器/重装/同步就丢用户的字段 —— 直接违背"数据可迁移" |

**倾向**：A2（记录变一个文件，元数据写在头部）+ 保留 `folder.json`（一个文件夹一个）。

### 方案块 B：用数据库加速（**只当索引，不当真相**）

现状是"每次刷新都翻一遍磁盘" —— 桌面上无所谓，安卓 SAF 上每次几十次跨进程查询，这是卡的根本原因。

| 候选 | 说明 |
|---|---|
| **B1** 引入本地索引库（应用私有目录） | 存"路径 → 解析结果"、照片元数据（EXIF/尺寸/哈希）、缩略图映射、将来的全文检索索引。**丢了能重建**。列表/照片库/搜索变成查索引 |
| **B2** 不引库，继续每次扫盘 | 简单，但安卓上快不起来；且记录一旦变成"一个 .md"，列 100 条就要读 100 个文件 |

**B1 的三条底线（必须写进工程契约）**：
1. **磁盘为准，索引可弃** —— 索引读不到/对不上就重建，永远不能只信数据库；
2. **先写磁盘，再更新索引** —— 中途崩了最坏是索引过期，不会丢数据；
3. **索引库放应用私有目录**，不进 Vault、不参与同步。

**对账做法**：不读内容，只看"路径 + 修改时间 + 大小"的指纹，变了的才重新读。首次进入或外部改动后仍需扫一次，之后就走索引。

**选型未定**：SQLite（`rusqlite`，将来全文检索方便）vs 纯 Rust 的键值库（交叉编译到安卓无 C 工具链风险，我们目前只需要"路径 → 解析结果"）。

### 方案块 C：照片的统一浏览（不依赖 A/B）

- 数据侧：`list_media()` 返回整个仓库的照片，每项带上"归属链拍平"后的字段（`entryId` 已有；补 `folderName`，v3 后补 `groupName`）。
  前端因此不需要理解目录层级。
- 视图侧：**一条日记一张卡片**（它那 1–3 张照片的小拼图）+ 顶部**文件夹筛选** + 点卡片进**全屏看这一条的照片**（可左右滑到相邻记录）；
  另给"不分日记的纯照片网格"。
- **前提**：**缩略图必须补齐**。现在只有导入那一刻生成；用户从文件管理器/桌面拖进来、被"收养"的照片没有缩略图 ——
  上千张的网格会去解码原图（安卓上很慢）。做法：扫描时按需生成 + 后台慢慢补，缩略图仍放应用数据目录（可重建、不进 Vault）。

### 方案块 D：记录要不要占一个目录

| 候选 | 形态 | 收益 | 代价 |
|---|---|---|---|
| **D1（现状）** 记录 = 目录 | `好卡/entry.json + note.md + 照片` | 照片归属是文件系统事实（拖进去就收养）；删除/撤销/改名/搬家都是一次目录操作；整条拖走 = 完整备份 | 用户侧不干净（见 A1）；目录层级多一层 |
| **D2** 记录 = 一个 `.md`，照片并排放在同一层（"同名成对"） | `2026-09-25 好卡.md` + `2026-09-25_随笔_01.jpg` | 用户侧最干净（就是笔记软件的形态）；层级更浅 | 归属变成**命名约定**：用户手动只改一半（改了 .md 没改照片）就只能靠扫描去猜；删除/改名要在应用里成对执行 |

**倾向**：D2（配合 A2），代价用"应用内操作总是成对执行 + 扫描对账能自愈"来兜。

## 7. 我们这边不可动的约束（评审时请当作前提）

1. **用户数据是开放的普通文件**：JSON / Markdown / 图片 / 视频；App 只是宿主。稳定边界是"Vault 规范 + 存储抽象"，不是界面。
2. **磁盘为准**：所有"归属"都由物理位置派生；用户在文件管理器里改名字、挪目录，扫一次就跟着认。
   手动改过的名字**永久保留**，系统永不覆盖。
3. **派生数据不进 Vault**：索引、缩略图一律放应用数据目录，随时可重建，永远不是真相来源。
4. **不引状态库 / 路由库 / UI 组件库**；编辑器引擎（CodeMirror 6）是唯一的框架级例外，只准出现在一个目录里、按需加载。
5. **安卓与桌面共用同一套领域逻辑与磁盘格式**（"桌面打的包传到手机要能直接导入"），
   平台差异只允许出现在指定的三个地方（窗口构建、SAF 后端、前端平台判断）。
6. **跨大版本不做兼容**：改布局 = 换 `SCHEMA_VERSION`，老仓库直接给中文报错（产品还没有真实用户）。

## 8. 落地顺序（按依赖，不是排期）

| 块 | 内容 | 依赖 | 能否独立验收 |
|---|---|---|---|
| **0** | 拆掉过渡桥、函数签名收窄 → 修 P1（字存不住）；顺便把 `list_entries` 按文件夹收窄 | 无 | ✅ 手机上能打字、编辑、删除、撤销 |
| **1** | 照片库（方案块 C，含缩略图补齐） | 无（不依赖 v3） | ✅ 照片页按日记成卡、点进去全屏 |
| **2** | 本地索引库（方案块 B1）+ 三条底线写进契约 | 无（不改磁盘形状） | ✅ 刷新不再扫盘、卡顿消失 |
| **3** | 记录变成"一个 .md" + 元数据进头部（A2 + D2）**+ 分组进数据（D1）+ 取消 `未归类` + 去掉 `folderId`** | 需要 1、2 就位 | ✅ 磁盘形状重写一次，端到端验收 + 文档同步 |
| **4** | 标签 UI + 批量多选/拖拽 + 聚合筛选视图 | 3 | ✅ |
| **5** | 相机拍完直接进仓库 | 无 | ✅ |

第 3 块是唯一会**重写磁盘形状**的一步，所以单独一次做干净（含 `docs/` 与 `AGENTS.md` 同步）。
