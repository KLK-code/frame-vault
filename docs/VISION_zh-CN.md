## 1. 产品定位与哲学

**产品本质**：以日记为底层载体的"**随心记**" —— 个人生活记录与连接平台，融合日记、相册管理、场景化打卡、灵感碎片记录。

> 现状标注：【部分有】PRD §1 的定位是"以照片和视频为核心、文字为辅助的影像日记 Vault"。
> 差异：本愿景把"日记/随心记"放首位（影像日记放在能力层）；"连接平台""灵感碎片"是新增叙事。
> ⚠️ 这是一处**定位重心的偏移**，动工任何门面功能前值得先拍板：第一叙事到底是"影像日记"还是"随心记"。

**产品哲学**：

- **0 门槛高上限**：默认体验极简，扩展能力极深。
- **精装房 + 可深度装修**：开箱即用，同时支持插件化定制。
- **老头环武器库**：大量场景，总有一款适合你。
- **削减用户心智负担**：一切自动化，用户只管记录。
- **核心极简，能力插件化，生态自生长**；经典默认 + 预装基础场景 + 插件市场。
- 让拍照重新有欲望，让记录重新有意义；修复"记录"这件事本身的体验，让照片变成记忆而非文件。

> 现状标注：【部分有】"渐进式复杂度"（PRD §2.2 原则 9）与双层用户画像已沾边；
> "精装房+装修""0门槛高上限"为新增提法。
> ⚠️ "核心极简、能力插件化"与 AGENTS §6 的判据有张力（编辑器、基础记录能力**必须进核心**，
> 否则一百个插件发明一百种数据格式）—— 详见 §5 冲突 3。

**终极愿景**：一个"**个人记录操作系统**"，让记录这件事变得无感。

> 现状标注：【部分有】PRD §2.1"可迁移、可扩展的个人记录"是其朴素版；提法本身全新。

## 2. 用户分层（四层）

| 层 | 画像 | 体验目标 |
|---|---|---|
| 普通用户 | 打开就是经典默认：拍照、写一句、保存，3 秒完成 | "打开就能用"，不知道有场景和插件 |
| 打卡/成长用户 | 用场景记录跑步、背单词、刷题，看趋势和成长数据 | 数据会说话 |
| 深度思考用户 | 随心记 → 深入记录，Markdown 长文，与 Obsidian 联动 | 挑剔用户觉得"软件懂我" |
| 技术/插件玩家 | 开发插件、分享场景、定制主题 | 探索时惊喜不断 |

> 现状标注：【部分有】PRD §3 已有三层（普通 / 高级 / 插件作者），本文切成四层并把"打卡成长"独立；
> "深度用户 + Obsidian"依赖 §4.8（尚无）。

## 3. 能力愿景全录

### 3.1 经典默认日记 【部分有】

- 打开即写，Markdown 实时渲染（Typora 式即时渲染），基于 CodeMirror 6（Obsidian 同款内核）。
- 光标所在处露出 Markdown 源码、移开即收回 → 已实施（2026-09-23，随内核换成 CodeMirror 6 一并落地，
  见 `docs/PROPOSAL_editor_codemirror6_zh-CN.md`；同日废弃的块级方案存档在
  `docs/PROPOSAL_wysiwyg_live_source_zh-CN.md`）。
- 中文输入法打磨（composition 事件，避免拼音打断渲染）→ 两处已知坑已登记（AGENTS §9）。
- 时间线、标签、搜索、图片、视频、同步、加密、导出。
- **经典默认是核心体验，不是初级模式**，要作为普通用户的第一印象细心打磨。
- 用户可卸载所有预装场景，软件变回纯粹 Markdown 日记本。

> 标注：所见即所得长文编辑已落地（写作台，内核为 CodeMirror 6）；"光标所在处露源码"已随内核一并落地；
> 输入法两坑已登记（AGENTS §9）；
> **"打开即写"（启动直达编辑态）是全新需求**，现 PRD 无记载。

### 3.2 场景化引擎 【部分有，含冲突】

- 原生内置 **20 个精细打磨的场景**（示例：跑步健身打卡、背单词、刷题、科研日记、读书笔记、旅行日志、
  随心记、情绪记录、工作日志……），每个场景有独立的数据结构、UI 模板、交互规则、统计视图、命名规则。
- 场景之间可联动：跑步+天气、读书+情绪、旅行+照片+地点等。
- 场景定义支持 DSL，用户可通过代码插件开发场景；基础场景也做成插件，只是默认预装。
- 用户可安装、卸载、分享场景插件；场景要一目了然，懒人用默认，高级用户玩插件。
- 场景识别与特化自动化，削减用户决策。

> 标注：机制地基已有 —— 文件夹级功能主题（PRD §4.9 / FV-WSP-001~004）、manifest 声明驱动 +
> 核心渲染表单（AGENTS §6，沾"DSL"边）、"主题是插件主扩展方向"（PRD）。
> 差异与冲突：**内置 4 个主题，不是 20 个**；**"每个场景独立数据结构"与 AGENTS §6 判据正面冲突**
> （会改变磁盘数据形状的能力必须进核心、全场景共用一种格式，否则 Vault 不再是开放格式）→ §5 冲突 3；
> 统计视图在 PRD 仅到 P2；场景联动、场景 DSL 全新。

### 3.3 拍照与视频 【部分有】

- 拍照和视频是**核心入口**，不是附属功能。打开软件第一屏应是"拍"或"记"，而非空白输入框。
- 拍照后流程：自动带时间地点 → 自动归属场景 → 可选写一句话 → 可选重命名 → 可选升级为深入记录。
- 拍照后提示重命名，但可关闭；关闭时按"日期 + 当前场景 + 内容字段"自动命名（见 3.5）。
- 视频与照片在数据模型中**平等**，共享场景归属、命名规则、关联逻辑；旅游场景尤其需要视频。
- 视频支持：缩略图生成、时长、分辨率、元数据提取、播放体验、压缩选项。
- 存储和同步围绕大文件设计：分层同步、断点续传、压缩可选。
- 回顾视图以视觉为主，照片和视频缩略图优先。

> 标注：相机是 P0 核心（PRD §5.3 / FV-CAM-001~005 / §11.1），但形态是"Entry 内调系统相机"，
> **"第一屏即拍/记"是新的产品形态**；EXIF 拍摄日已用；地点自动归属现在只有旅行主题手工填写；
> 视频导入/播放 P0、缩略图与断点续传 P1 已排；时长/分辨率展示、压缩选项未记载；
> ffmpeg 抽帧在 AGENTS §10 仍为推迟项。

### 3.4 随心记与深入记录 【部分有】

- 随心记：移动端拍照 + 短文本，无压力快速捕捉。
- 深入记录：桌面端 CodeMirror 6 即时渲染 Markdown，沉浸式长文编辑。
- 用户主动将"随心记"**升级**为"深入记录"，有仪式感：进入编辑草稿态，可反复修改，确认后正式升级。
- 数据模型共享，转换只是字段扩展，不丢数据。
- 心流状态：打开相机一秒，拍完三秒存好，不强制任何操作。

> 标注："记录方式分两派"已定案（README：快速记录三主题 + 写作台），Entry 模型共享。
> 差异：现行定案是**并存**（快记主题"保留不动"），本文提出的是**升级链路**（移动快记 → 桌面长文）+
> "草稿态仪式感"，为新增交互，未记载。

### 3.5 自动化与命名 【部分有】

- 自动命名从场景级到内容级：
  - 场景级：`2026-09-23_跑步挑战_5公里_01.jpg`
  - 内容级：`2026-09-23_读书笔记_百年孤独_01.jpg`
- 命名模板支持内容变量（日期、场景、书名、实验编号、地点……）。
- 回退策略：无内容字段 → 场景级；无场景 → 经典默认（日期+时间+地点）。
- **数据库关联优先于文件名**，文件名只是友好标识；用户手动改名后系统不覆盖。
- 同一天同一场景多张照片加序号或时间戳后缀；跨设备同步冲突加设备标识或随机串。
- 自动命名让整理成本从用户转移到系统。

> 标注：Entry 模板默认标题已有（FV-ENT-004）；"数据库关联优先"精神与现行铁律一致且更强
> （AGENTS §3 铁律 8：磁盘名固定 `orig.<ext>`、原名进 meta）。
> ⚠️ 与**存储规范 v2 提案**衔接：v2 已拍板"媒体用原始文件名"，自动命名模板恰好就是
> v2 落地后"导入时生成友好文件名"的实现层 —— 两件事应合并设计。
> 命名模板 / 回退策略 / 冲突后缀为全新需求。

### 3.6 关联与发现 【部分有】

- 显式关联：双链、标签、人物、地点。
- 隐式关联：时间关联（往年今日）、内容相似（语义相似）、场景交叉、反向链接（自动维护）、
  人物/地点关联、情绪趋势。
- 技术路径（排期意图）：先做**时间关联 + 显式双链**，再做语义相似（本地向量搜索或关键词提取，放 Rust 侧）。
- 照片关联：利用 EXIF 时间、地点，自动和同时间段日记关联；写日记时自动推荐"同一天拍摄的照片"。
- 让碎片记录串成网，让数据"活"起来。

> 标注：标签/日期筛选（FV-ENT-003 / FV-UI-004）、往年今日（FV-UI-006 P2）、快速搜索（FV-UI-005）、
> 旅行地点时间线已有；**双链、人物、反向链接、语义相似、向量搜索全新**。
> ⚠️ 边界：PRD §10"AI 人脸/语义识别不做"、AGENTS §10"全文检索还没到，别提前设计" ——
> 语义相似动工前需先修订这两条。

### 3.7 相册迁移 【全新】

- 第二阶段高级功能：导入普通相册，基于 EXIF 时间、地点自动归档。
- AI 辅助识别场景标签（轻量级端侧模型如 MobileNet、CLIP）。
- 多模态信息融合（时间、地点、画面内容）生成有意义的命名和摘要；场景映射引擎把 AI 标签与用户场景自动关联。
- 性能：高效批量处理流水线、后台任务、增量索引。
- 分层策略：第一层 EXIF 归档（必做）→ 第二层轻量端侧模型标签（选做）→ 第三层多模态生成日记草稿（远期）。

> 标注：全新需求，PRD 无相册迁移条目。EXIF 读取已有（FV-MED-004/005，仅单条导入属性）。
> ⚠️ 第二、三层贴着 PRD §10"AI 语义识别不做"的红线（灰色地带），见 §5 附注。

### 3.8 Obsidian 联动 【全新】

- 为 Obsidian 开发插件，双向互补：本软件负责生活记录、照片、碎片灵感；Obsidian 负责知识管理、深度分析。
- 结构化数据导出给 Obsidian 做分析；Obsidian 长文灵感可摘要回流，与当天场景关联。
- 先做单向导出，再做双向同步；场景插件可与 Obsidian 联动；各司其职，形成"记录-分析"闭环。

> 标注：全新需求，PRD 无记载。仅有精神渊源：文件夹组织"类似 Obsidian"（PRD §4.8）、
> 存储规范 v2 提案的"Obsidian 式人可读层级"。

### 3.9 插件与生态 【已有】

- 一切皆插件，基础场景默认预装；插件市场：用户可开发、提交、下载场景插件（GitHub/Gitee 托管、审核上架）。
- 插件 API 必须稳定，文档、示例、调试工具齐全（开发者文档像产品一样对待）。
- 质量与安全：审核机制、权限模型、沙箱隔离；插件崩溃不影响核心；预装与第三方权限一视同仁。
- 插件按需加载、生命周期管理、启动性能优化；插件间通信走统一数据总线/事件系统。
- 边界：同步、加密、编辑器内置；场景、自动化、联动插件化。
- 插件发现：分类、评分、推荐、合集。
- 路径：先自己按第三方标准写插件验证 API → 信任开发者内测 → 公开市场；生态冷启动靠官方场景证明 API 稳定性。

> 标注：PRD §6.4（FV-PLG-001~012：权限/隔离/Marketplace/侧载/Registry/SDK）、§5.7 安装流程、
> §7.3 签名与来源已在，且"先按第三方标准自写验证"已在执行（写作台只用公开接口、M3 用内置主题验证扩展点）。
> 小缺口：生命周期钩子、审核细则未展开；"数据总线"现仅到插件事件（FV-PLG-006）。

### 3.10 同步与加密 【部分有，含冲突】

- 端到端加密：本地加密 + 传输加密；密钥管理、设备配对、密钥轮换、恢复流程、多设备冲突。
- 加密后冲突合并在客户端计算，服务端只存密文；场景结构化数据加密粒度（全量或字段级）。
- 元数据保护（文件大小、修改时间、设备数量）。
- 云同步国内优先：坚果云 WebDAV、中国科技云数据胶囊、123 云盘、天翼云盘、移动云盘等；原生 WebDAV 覆盖 NAS。
- 自建云最后搞：自建云 + 订阅模式（免费本地，付费云同步、多设备、版本历史、更大空间）。
- 数据迁移引擎：场景版本管理，用户自定义数据结构迁移。
- 本地数据安全：自动备份、导出 Markdown + 图片文件夹、版本历史；导入导出顺滑，可手动迁移设备。

> 标注：已有坚果云（FV-STO-005）、百度/阿里（PRD §6.5）、冲突不静默覆盖（FV-SYN-006）、
> 凭证保管（stronghold）；**E2E 加密是 PRD §12 第 1 条待决项**（非拒绝）。
> 冲突：①"自建云 + 订阅制" vs PRD §10"自建云存储服务不做"→ §5 冲突 2；
> ② LWW 未记载且与"不静默覆盖"相悖 → §5 冲突 4；③ 123/天翼/移动云无记载（占位"未来其他网盘"）。

### 3.11 多端与平台 【冲突待裁决】

- 桌面端：Tauri + Rust + TypeScript + React + CodeMirror 6（与现行基线一致，2026-09 换内核）。
- 移动端：优先复用同一套 Rust 核心，UI 层接受 WebView 手感；可考虑 React Native 混合方案，
  编辑器内核（CodeMirror 6）本来就在 WebView 里跑，嵌进去不换栈。
- 三端适配：Windows、Mac、Android（后续 iOS）；响应式、安全区、触控区域、手势。
- 图片加载走自定义协议（asset://），避免 IPC 瓶颈；视频播放考虑系统原生播放器兜底。
- 跨平台文件系统权限、后台限制差异需处理。

> 标注：Tauri 路线与现行一致；asset 协议已开（Tauri 内置 `assetProtocol`，非自定义协议）；
> 手机骨架已起步（MobileShell）。**React Native 混合 + uniffi 与 AGENTS §1 技术基线锁定正面冲突** → §5 冲突 1。

### 3.12 技术栈与架构 【部分有】

- 技术栈：Tauri 2.x、Rust、TypeScript、React、CodeMirror 6（2026-09 由 Milkdown/ProseMirror 换成它，现行基线 ✅）。
- SQLite 本地存储，CRDT 或 last-write-wins 冲突策略（⚠️ 见 §5 冲突 4）。
- libsodium 加密、ffmpeg 视频处理、uniffi 绑定（⚠️ 后两者见冲突清单）。
- 插件加载器、运行时、数据总线、事件系统；场景定义 DSL（声明式配置 + 代码插件）。
- 数据模型带设备来源和全局唯一 ID，为同步准备；本地库设计为可同步结构（时间戳、版本号、变更日志）。
- 启动性能：懒加载、按需加载、内存释放；插件沙箱隔离或容错。

> 标注：SQLite 定位已锁死（仅索引/缓存，AGENTS §3.3）；懒加载纪律已在（编辑器按需加载）；
> libsodium / DSL / 设备来源字段 / 可同步结构为新增设想。

### 3.13 商业化 【全新】

- 主程序免费，经典默认免费；高级插件、官方精选场景、企业定制场景收费。
- 订阅制：云同步、多设备、版本历史、更大空间。
- 场景市场：付费场景分成、场景作者打赏。
- B 端和团队版：科研日志、实验记录、项目复盘。
- 用户为"省心"付费，而非为"功能"付费。
- 前期不赚钱，贴钱，靠热情和用户反馈撑；目标：一个人或小团队，靠软件过上体面、自由、可持续的生活。

> 标注：零记载（仓库仅 Apache-2.0 许可）。"B 端团队版"与 PRD §10"实时协作编辑不做"有张力但非直接冲突。

## 4. 开发节奏与内测

- 大节奏：先三端本地体验 → 再（第三方）云 → 最后插件生态 —— 与 PRD §9 里程碑 M0→M5 顺序吻合。
- 阶段目标：一个月全职做到界面交互 80-90%、3-5 个核心场景能用、数据层初步成型；
  先把 3-5 个场景做到"惊艳"，再扩展；一个月后给 5-10 个真实用户内测收集反馈。
- 联动先做时间+场景，再做语义+跨场景；Obsidian 先单向导出；相册迁移属第二阶段。
- 守住边界：核心只做核心，一切扩展走插件；克制"加按钮"冲动，防止核心膨胀。
- 个人成长并行：持续补数据结构、OS、计组、网络、数据库；每天算法题 + 读项目代码，每周技术笔记。

> 标注：【部分有】里程碑骨架吻合；"一个月 / 内测人数"是新增的时间承诺，PRD 刻意不含排期 ——
> 是否写入正式计划由作者自行决定（学习项目，弹性优先）。
